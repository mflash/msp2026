Origem e Filosofia

O Git em Três Ideias

2005: Linus Torvalds interrompe o kernel Linux para escrever a ferramenta que o versionaria

1. Distribuído

Todo clone é um repositório completo, com o histórico integral do projeto.

Dá para commitar, criar branches e consultar o log offline, no avião ou sem internet.

2. Snapshots

Cada commit é uma fotografia do projeto inteiro, não uma lista de diferenças.

Arquivo que não mudou vira só um ponteiro para a versão já guardada: sem desperdício de espaço.

3. Hashes

Cada commit inclui o hash do commit anterior.

Alterar o passado muda o hash daquele commit e de todos os seguintes: qualquer adulteração é detectável.

⚠️ Todo o histórico mora na pasta oculta .git/. Apagá-la destrói o histórico daquela cópia (os arquivos atuais ficam, os commits se perdem).

- 2 minutos. Contar a história do BitKeeper em uma frase e seguir para as três ideias. - Reforçar o alerta do .git/: é um erro comum ao "limpar" o projeto ou copiar pastas.
Modelo Mental

As Quatro Áreas e os Estados do Arquivo

A jornada de uma alteração entre o seu teclado e o repositório da equipe:

Do Teclado ao Repositório

Untracked Modified ➔ add ➔ Staged ➔ commit ➔ Committed 
git status                    # o que mudou?
git add arquivo.c             # prepara (Staging)
git status
git commit -m "Adiciona soma" # grava o snapshot
git log --oneline             # histórico resumido
git push                      # envia ao remoto

Por que a Staging Area existe?

Ela permite escolher o que entra em cada commit: quebrar uma grande edição em commits pequenos, atômicos e explicáveis.

- 4 minutos. Ao vivo: git status; git add arquivo; git status; git commit -m "..."; git log --oneline. - Mostrar como o git status muda de "Untracked/Modified" para "Changes to be committed".

🔑 Commitou uma senha?

Apagá-la num commit novo não basta: ela continua no histórico, em todos os clones. É preciso trocar a credencial.

- 1 minuto. O alerta da senha é o ponto mais importante: consequências reais (chaves de nuvem vazadas em repositórios públicos são exploradas em minutos).
O Superpoder do Git

Branches e os Dois Tipos de Merge

Regra de ouro: nunca trabalhe direto na main

git switch -c feature/login  # cria e muda
# ...edita e commita na branch...
git switch main
git merge feature/login
  • Fast-forward: a main não mudou desde que a branch nasceu. O ponteiro só avança; o histórico segue em linha reta.
  • Merge commit: os dois lados mudaram. Surge um commit especial com dois pais unindo as linhas.
  • Históricos divergentes na maioria das vezes NÃO geram conflito: se mexeram em linhas diferentes, o Git combina sozinho.
- 3 minutos. Mostrar a palavra "Fast-forward" na saída do merge e, no outro caso, "Merge made by the 'ort' strategy". - Preparar o terreno: o conflito só é possível no segundo caso.
Sem Pânico

Conflito de Merge: o Git Pedindo Ajuda

A main define a porta 8080; a feature/login define 9000, na mesma linha do config.h 

git merge feature/login
# CONFLICT (content): Merge conflict in config.h
git status          # both modified: config.h
cat config.h

# editar: escolher a versão e apagar os marcadores
git add config.h    # marca como resolvido
git commit -m "merge: resolve conflito de porta"
<<<<<<< HEAD
#define PORTA_SERVIDOR 8080   // versão da main
=======
#define PORTA_SERVIDOR 9000   // versão da feature
>>>>>>> feature/login

O conflito não é bug: é o Git se recusando a adivinhar e pedindo que um humano decida.

🚪 Saída de emergência: git merge --abort devolve tudo ao estado anterior, sem perder nada.

- 5 minutos. Usar o mini-repositório preparado (main com 8080, feature/login com 9000 no config.h). - Comparar com o diagrama do slide anterior: o histórico é igual, só que agora as duas branches mexeram na mesma linha. - É o momento em que os alunos mais travam em trabalhos em grupo.
Trabalho em Equipe

Remoto e Pull Requests

O primeiro susto de quem começa a usar o GitHub em grupo:

git fetch vs. git pull

  • fetch: só baixa; não toca nos seus arquivos. Seguro para olhar.
  • pull = fetch + merge: por isso um pull também pode gerar conflito!

O erro "divergent branches"

hint: You have divergent branches and need to
hint: specify how to reconcile them.
fatal: Need to specify how to reconcile divergent branches.

Resolva uma vez por todas: 

git config --global pull.rebase false

O Fluxo do Pull Request

Na equipe, ninguém faz merge direto na main do servidor: 

# envia a branch e cria o vínculo (-u)
git push -u origin feature/login
  1. push da branch
  2. abrir o Pull Request no GitHub/GitLab
  3. revisão pelos colegas (e ajustes)
  4. só então o merge na main

🎯 O PR garante que outra pessoa sempre olhe o código antes de ele chegar à main.

- 2 minutos. Conectar: o pull que falha é um merge, e já sabemos lidar com merge e com conflito. - O resto (--amend, revert, reflog, chaves SSH) fica para estudo no material.
