Fundamento Teórico

A Mentalidade: Medir Antes de Otimizar

Depuração responde "por que falhou?"; Profiling responde "onde gasta recursos?"

Donald Knuth

"A otimização prematura é a raiz de todos os males na programação."

Escreva código legível e correto primeiro. Otimize apenas o que o profiler acusar.

Princípio de Pareto (80/20)

Em média, 80% do tempo de execução é consumido por apenas 20% do código (laços críticos e I/O).

A intuição humana costuma errar feio onde esses 20% estão localizados!

Lei de Amdahl

O ganho global é limitado pela fração do tempo que o trecho acelerado realmente ocupa:

  • Acelerar 4× algo que gasta 80% ➔ 2,5× mais rápido.
  • Acelerar infinitamente algo que gasta 5% ➔ só 5% de ganho!
- Enfatizar os números de Amdahl: gastar semanas reescrevendo uma função que gasta 2% do tempo é desperdício de tempo e dinheiro.
Diagnóstico Confiável

Do print ao Logging Estruturado

Por que a engenharia de software substitui prints espalhados por logs com metadados:

As Limitações do print

  • Polui a saída padrão: mistura depuração com dados do pipeline no stdout.
  • Falta contexto essencial: não traz data/hora, severidade nem arquivo/linha.
  • Perda em falhas críticas: em crashes (como Segfault em C), o buffer do stdout pode não descarregar a tempo.
  • Sem controle seletivo: impossível silenciar sem editar ou apagar o código antes de ir para produção.

Logging Estruturado e seus Níveis

Canalizado por padrão ao stderr com metadados automáticos:

DEBUG INFO WARNING ERROR CRITICAL

💡 O poder do Filtro Global: Em produção, basta ajustar o nível mínimo para INFO para ocultar todos os DEBUG automaticamente — sem tocar em nenhuma linha de código da aplicação!

- Lembrar que logging escreve no stderr (canal 2) por boa prática, mantendo o stdout livre para dados. - Destacar que o nível é hierárquico: definir INFO descarta DEBUG; definir WARNING descarta INFO e DEBUG.
Instrumentação Prática

Logging na Prática: Código e Terminal

Como instrumentar código em Python e processar eventos no terminal:

Código Python com logging (faturamento.py)

import logging

logging.basicConfig(
    level=logging.DEBUG,
    format="%(asctime)s [%(levelname)s] %(message)s"
)
logger = logging.getLogger("Faturamento")

def calcular_desconto(preco, percentual):
    logger.debug(f"Calculando: {preco=}, {percentual=}")
    if percentual > 50:
        logger.warning(f"Desconto suspeito: {percentual}%")
    if percentual < 0:
        logger.error(f"Percentual invalido: {percentual}")
    return preco * (1 - percentual / 100)

Uso e Filtragem no Terminal (Módulo 02)

# 1. Executa direcionando logs (stderr) para arquivo
python3 faturamento.py 2> app.log

# 2. Filtra apenas anomalias graves (tempo real)
grep -E "WARNING|ERROR" app.log

# 3. Estatística de severidade com pipeline Unix!
grep -oE "\[(DEBUG|INFO|WARNING|ERROR|CRITICAL)" app.log \
  | sort | uniq -c

💡 Os logs gravam no stderr e são analisados com
grep | sort | uniq -c!

- Mostrar a conexão direta entre o módulo de logging em Python e as ferramentas Unix do Módulo 02 (grep, sort, uniq, 2>).
Visualização Avançada

Como Ler um Flame Graph

O mapa visual definitivo do consumo de CPU:

Guia de Leitura Visual

  • Eixo Y (Vertical): profundidade da pilha de chamadas (call stack). A função chamadora fica embaixo, as chamadas ficam em cima.
  • Eixo X (Horizontal): proporção do tempo gasto (100% da largura). A ordenação é alfabética, NÃO é linha do tempo!
  • 🎯 Onde está o gargalo?
    NÃO é o bloco mais largo da base (main sempre é 100%). O gargalo são os platôs do topo: blocos largos sem nada empilhado acima!
- Alerta essencial: muitos acham que o eixo horizontal é o tempo correndo da esquerda para a direita. Não é! É percentual agregado.

Caso Real C/C++

Profiling em C com Callgrind & KCachegrind

A investigação do processamento.c: 5× mais rápido com poucas linhas!

A Surpresa da Investigação

  • funcao_lenta_gargalo respondia por 99,8% do tempo.
  • O profiler revelou que 90% desse tempo estava dentro de cos(), chamada 40 milhões de vezes!
  • Mas cos(j) só recebia 2.000 valores distintos: o código recalculava o mesmo cosseno 20.000 vezes!
  • Correção por Memoização: pré-calcular os 2.000 valores em um vetor fez o tempo cair de 0,63 s para 0,13 s (5× mais rápido)!
- Notar que o compilador GCC (-O2) otimizou o sin() para fora do loop automaticamente, mas não pôde otimizar o cos() com j dinâmico. - Mostrar que a investigação guiada por profiler gerou 5x de ganho mexendo apenas no ponto cirúrgico.
Caça a Bugs de Memória

Vazamentos de Memória com Valgrind

Encontrando malloc sem free na linha exata:

Detecção Automática no vazamento.c

# Compilar com símbolos de depuração (-g)
gcc -g vazamento.c -o vazamento

# Executar sob inspeção do Valgrind Memcheck:
valgrind --leak-check=full ./vazamento

Relatório do Valgrind:
